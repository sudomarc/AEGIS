# AEGIS Submission Checklist

## Required public deliverables

### Devpost
- [ ] Project title.
- [ ] Official track selected.
- [ ] Problem statement.
- [ ] Target users.
- [ ] Solution description.
- [ ] Technical approach.
- [ ] Real-world impact.
- [ ] All team members listed.
- [ ] One final submission only.

### Demo
- [ ] Public video.
- [ ] 2–4 minutes maximum.
- [ ] Problem shown first.
- [ ] Working demo shown live/recorded.
- [ ] AI behavior visible.
- [ ] Impact explained.
- [ ] No unsupported claims.

### Repository
- [ ] Public GitHub repository, unless organizers instruct otherwise.
- [ ] README is complete.
- [ ] Installation/setup instructions work.
- [ ] Environment variables documented without secrets.
- [ ] Architecture diagram reflects reality.
- [ ] Tests or evaluation procedure documented.
- [ ] Model/provider choices documented.
- [ ] License compatibility checked.

## Final technical gates

- [ ] Production/preview URL tested.
- [ ] Fresh-page load tested.
- [ ] Golden path tested.
- [ ] Error path tested.
- [ ] Rate/time/output limits reviewed.
- [ ] No credentials committed.
- [ ] Dependencies are intentional.
- [ ] Browser/viewport verification completed.
- [ ] Final diff inspected.
- [ ] Final repository status inspected.

## Story consistency

The following must tell the same story:

**Problem → User → Solution → AI → Evidence → Impact**

If the video claims a capability that is not present in the submitted code, fix the implementation or change the claim.
